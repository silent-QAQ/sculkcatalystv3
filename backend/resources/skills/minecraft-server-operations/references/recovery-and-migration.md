# 数据保护、备份、恢复与迁移

## 备份原则

- 采用 3-2-1：至少三份副本、两种介质、一份异地；备份目录和线上服务器分开权限。
- 必备内容通常包括世界目录、`server.properties`、核心启动文件、插件/模组清单与配置、权限/经济/数据库导出、资源包和启动脚本；按实际数据源补充。
- 执行备份前发送 `save-all` 或按核心支持的安全保存流程，再停止服务器或使用一致性快照。正在写入的世界和数据库不能直接复制当作可靠备份。
- 定时任务保留轮换策略并定期做恢复演练；“备份文件存在”不等于“可以恢复”。

## 恢复

- 单世界问题：停止服务、先备份当前损坏状态、恢复目标世界、启动并检查日志/出生点/区块/玩家数据。
- 全量恢复：停止服务，保留损坏现场，恢复完整目录和匹配版本，启动后验证插件、数据库、权限和玩家数据；确认恢复成功前不要删除损坏副本。
- 只恢复插件配置：先在临时位置对比版本和 schema，只复制所需文件；不要把新版本配置盲目覆盖旧版本。
- 玩家破坏优先考虑 CoreProtect 的可审计局部回档；数据库损坏优先使用数据库备份或导出，不用复制正在运行的数据库目录碰运气。

## 升级与回滚

1. 记录旧核心、Java、插件/模组、配置和数据库版本，做完整备份并规划维护窗口。
2. 新建测试目录，放入目标核心并单独启动一次生成默认文件；同意 EULA 后停止，确认 Java 与端口。
3. 逐项检查插件/模组发布信息和兼容矩阵；按 1～2 个组件一组启动，出现首个错误就停下来处理，不要一次性换完所有 JAR。
4. 世界升级让目标版本自然转换，保留日志和迁移时间；大世界转换期间不要强制中断。配置按键逐项迁移，不要直接覆盖 `server.properties`、Paper/Spigot 或插件配置。
5. 用目标玩法、spark 基线、玩家登录、权限、数据库、资源包和备份恢复路径做验证；保留旧版本至少一个观察窗口。

禁止直接跳过多个世界格式版本、在升级后用旧版本回写同一份世界、或没有备份就做降级。需要回滚时恢复升级前完整目录和数据库，并说明升级后产生的数据会丢失。
