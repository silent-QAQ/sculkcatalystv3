# 基础选型、JVM、部署与安全

## 核心与加载器

- 普通插件服默认从 Paper 开始：Bukkit/Spigot 生态最完整，适合普通生存、RPG 和小游戏；如果目标是插件生电，不采用这条默认路径。
- Purpur 是 Paper 的玩法定制分支，适合明确需要额外玩法开关的服务器；不要因为“配置多”就默认启用所有选项。
- Leaves 适合重视红石、生物 AI、区块加载等原版机制的插件服；Pufferfish/Leaf 适合明确的高负载/TPS 场景，但需要验证深度 Hook 插件。
- Folia 是区域化多线程架构，适合玩家分散的玩法；玩家密集、强依赖传统主线程和大量 Bukkit 插件的服不应直接选它。Luminol、Lophine、Kitin 等 Folia 分支也必须逐个验证。
- 模组服使用 Fabric、Forge 或 NeoForge；模组、插件、客户端模组和数据包属于不同生态。只有在明确兼容矩阵和测试结果后才考虑混合端。
- 插件生电优先选择 Leaves：它兼顾 Bukkit/Paper 插件生态和较高的原版机制还原度。只有接受模组生态、追求纯机制还原时才选择 Fabric + Carpet；追求多线程时再评估 Lophine/Luminol，并接受更高兼容风险。

## Java 与 JVM

- 现代核心通常优先检查 Java 21；老版本按核心、模组和插件构建链实际要求选择，不要用“系统默认 Java”猜版本。
- 内存分配取决于玩家数、世界数量、视距/模拟距、实体、插件、模组和数据库。保留操作系统余量，调参后用实际 GC、TPS 和延迟验证。
- Aikar's Flags 可以作为 Paper 类服务器的起点，但不能替代 Java 版本检查、硬件评估和 spark 数据；模组服要按其启动器和模组包要求调整。
- 启动脚本应固定工作目录、明确 JAR、日志位置、最大/最小内存和优雅停止方式；不要把多套 Java 路径、旧 JAR 和新 JAR 混在同一目录而不标识。

## Linux 与群组代理

- Linux 部署使用专用的非 root 用户运行 Minecraft；服务器目录、备份目录和凭据目录分离权限。
- screen 适合人工维护，systemd 适合开机自启、日志和重启策略；无论哪种方式都要保留优雅 stop 路径。
- Velocity 负责群组入口，后端服务器只接受来自代理的流量。配置转发密钥、玩家信息转发模式和后端白名单时，代理与后端必须成对验证。
- 公网只暴露必要端口；RCON、数据库和管理端口默认只监听回环或内网，使用 UFW/云防火墙限制来源，并考虑 fail2ban 和 SSH 密钥登录。
- Geyser 的 UDP 端口、代理端口和后端端口要分别记录；不要因为 TCP 端口可达就认定基岩版链路完整。

## 安全基线

- `online-mode`、白名单、OP、权限组、RCON 密码、代理密钥和数据库凭据按最小权限配置；凭据不写入仓库、公开日志或聊天回复。
- 安装插件前确认来源、实际 JAR、目标核心/版本、依赖和许可证；付费、闭源、网盘或不可验证构建应降级为人工审核。
- 先备份再改配置；不要为了“解决连接问题”关闭正版验证、开放管理端口或扩大 OP 权限。
