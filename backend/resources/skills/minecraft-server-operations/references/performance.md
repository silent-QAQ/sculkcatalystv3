# 性能、Paper 配置与容量判断

## 诊断顺序

1. 先记录基线：在线人数、TPS/MSPT、CPU、内存/GC、磁盘 IO、网络延迟、视距/模拟距、实体数、区块加载和最近变更。
2. 用 spark 先做 health report，再按时间窗口做 profiler；需要时用 Timings v2 做对比。报告要对应具体时段和负载，不能凭单次峰值下结论。
3. 按热点归因：`Entities/tick` 通常看实体/刷怪/农场，`TileEntities` 看漏斗/箱子/方块实体，`Plugin/tick` 看插件任务；同时检查区块生成、玩家集中位置和数据库/磁盘 IO。
4. 一次只改一组相关配置，重启或按要求重载后复测同一场景；保留原配置和报告，确认收益没有破坏机制或玩家体验。

## Paper 系列配置

- `server.properties` 决定基础端口、视距、模拟距、在线验证、白名单和资源包等运行边界。
- `bukkit.yml`、`spigot.yml`、`paper-global.yml`/`paper-world-defaults.yml` 和 `purpur.yml` 层级不同；先确认当前版本文件名和作用域，再改对应位置。
- 实体激活/追踪范围、漏斗合并、区块加载和生物生成是常见热点，但它们可能改变刷怪、红石、战斗和插件行为；技术生存不要套用通用优化值。
- 不要直接把网上的“万能 Paper 配置”覆盖进服务器。每个参数都要说明目标、预期收益、机制影响和回滚值。

## 容量与工具

- 20 TPS 不是永久保证；玩家集中、世界生成、大型农场、插件任务、数据库写入和网络抖动都可能改变结果。
- 承载量只能通过目标硬件、版本、玩法、地图、插件/模组和真实压力测试得出；知识库中的对比数字仅作同一条件下的趋势示例。
- spark 适合持续分析、火焰图和内存观察；Timings 适合兼容场景下的任务对比；两者都需要明确采样窗口并在结论中标注证据。
- ClearLag 不应当一键清理所有实体。保护命名生物、村民、农场和剧情实体，优先设置有边界的实体策略并验证玩法。
