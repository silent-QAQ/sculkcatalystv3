# 插件、模组、数据库与内容组件

## 选型与安装顺序

1. 先确定服务器类型和核心，再按职责分层：权限、基础指令、保护/回滚、变量/展示、经济、玩法、性能和互通。
2. 同一职责优先只选一个主插件；检查前置依赖、API 版本、Java 要求、Folia 支持、数据迁移能力和维护活跃度。
3. 推荐来源顺序为 Modrinth、Hangar、GitHub Release、官方 Jenkins/CI，再考虑社区镜像；页面、源码包、配置包和 JAR 要区分。
4. 下载前校验项目、版本、加载器、文件类型和摘要；下载后检查 ZIP/JAR 内容、插件描述文件和启动日志，不能把 HTML 错误页当插件安装。

常见基础层可以按需组合 LuckPerms、Vault、EssentialsX、WorldGuard/GriefPrevention、CoreProtect、PlaceholderAPI、TAB 和 spark；这只是职责清单，不是要求全部安装。RPG、菜单、自定义物品、NPC、任务和经济插件要根据同一版本的兼容矩阵逐层加入。

## 配置与排错

- 先确认插件版本和官方默认配置，再备份后只修改关键项；复杂插件分阶段启用，启动一次验证一次。
- 排错顺序：确认插件是否加载 → 读取启动日志 → 检查前置依赖 → 检查核心/MC/Java/Folia 兼容 → 检查配置格式、路径、权限和数据库连接 → 最后才考虑插件冲突。
- 发生命令冲突、PlaceholderAPI 变量为空、ProtocolLib/PacketEvents 不匹配、经济未注册或 Folia 调度异常时，先缩小到最小插件集复现。
- 配置输出应列出文件路径、改动键、原值/新值、是否需要重启、依赖和回滚方法；不要生成整份配置覆盖用户已有注释和未提及设置。

## 模组与混合端

- Fabric 适合轻量和性能模组；Forge/NeoForge 适合整合包和模组生态。服务端模组、客户端必需模组、Fabric API/NeoForge 前置必须分开列出。
- 混合端（如 Arclight 类方案）把两个生态的生命周期和线程模型叠加，只有在目标插件/模组明确支持并完成回归测试后使用；不要把它作为新手默认方案。
- 崩溃先看 `latest.log`、崩溃报告、模组加载阶段和首个异常，不要只看最后一行。移除或禁用单个可疑组件时先备份并记录变更。

## 数据库

- SQLite 适合单机、小规模和插件默认场景；MySQL/MariaDB 适合多服共享或需要集中维护的数据；Redis 只在插件明确支持并有数据一致性方案时使用。
- 数据库账号只授予目标库所需权限，限制监听地址和防火墙来源；连接串、密码和密钥不能进入版本库。
- 配置数据库插件时先做 schema/备份确认，再验证连接、写入、重启后读取和断线重连；不要把“能启动”当作数据链路验证完成。

## 场景组合

- 小型好友生存：Paper + 少量基础插件，优先稳定、备份和权限，不追求复杂堆栈。
- 公益生存：在基础层上增加保护、回滚、性能监控和社区功能，先验证数据库与备份。
- RPG：先固定核心、版本和依赖顺序，再逐组加入任务、技能、属性、怪物、模型、菜单和 NPC，重点测试资源包、经济和性能。
- 空岛/小游戏/PvP：世界模板、快速重置、实体和区块策略优先；小游戏不要照搬生存服的生物和视距配置。
- Java+基岩：Geyser/Floodgate、权限、资源包和代理要按同一版本联调，不能只安装两个 JAR 就宣布互通完成。
